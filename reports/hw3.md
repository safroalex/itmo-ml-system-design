# ДЗ №3. Оценка релевантности компаний

## Состояние эксперимента

| Требование | Что подготовлено | Что остаётся |
| --- | --- | --- |
| Бейзлайн и основная модель, 6 баллов | Предобработка, бланки независимой разметки, групповое разбиение, TF-IDF с логистической регрессией, локальный LLM-классификатор, расчёт метрик | Обучить и оценить на согласованном эталоне, приложить агрегаты с реальных прогонов |
| Подготовка пилота, 4 балла | [Раздел 4 дизайн-документа](../docs/ml_system_design_doc.md#4-подготовка-пилота) описывает распределение задач между менеджерами, критерии успеха, бюджет и подготовительные шаги | Проведение пилота относится к следующему этапу проекта |

В [EDA](eda.md) зафиксировано 1 171 наблюдение для 79 запросов с непустой выдачей.
В репозитории хранятся агрегаты. Для прогона необходимы исходные локальные файлы.
Книга запросов менеджеров содержит запросы, ссылки и теги сценариев. В ней отсутствуют
тексты карточек отдельных компаний и ручные решения об их релевантности. Метрики
качества обеих моделей на реальных парах пока не измерены.

## 1. Подготовить критерии и зафиксировать разбиение

Для приведённых команд используется Python 3.12. Пути указаны от корня проекта.

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-models.txt
python scripts/hw3_data.py criteria --snapshot data/raw/dealrocket \
  --dialogues data/raw/dealrocket_admin/conversations.jsonl --out data/work/criteria.csv
```

Скопировать из снимка ДЗ №2 `queries.csv` и `pairs.csv` в
`data/raw/dealrocket/`. Если исходные диалоги недоступны, опустить `--dialogues`
и восстановить в бланке `dialogue_ids` по отдельному соответствию запросов диалогам.
Самостоятельный идентификатор для каждого хода одного диалога приведёт к утечке.
В каждой строке эксперт заполняет `criteria` обязательными условиями через
вертикальную черту, сохраняет исключения и указывает `status=confirmed`.
Для запросов без критериев профиля ставит `exclude`. Общий `related_group`
позволяет объединить близкие по смыслу запросы с разными формулировками.

```bash
python scripts/hw3_data.py split --snapshot data/raw/dealrocket \
  --criteria data/work/criteria.csv --out data/work/split
```

Компоненты связности объединяют общие компании, диалоги, критерии и дополнительные
группы. Разбиение выполняется до разметки. Стремимся к равному числу запросов
в разработке и тесте. Если фактический баланс сильно отличается от 40/40 или
компонента охватывает более четверти запросов, действуем по §3.2 до разметки.
Сохраняем выбранные группы и фолды вместе со снимком.

## 2. Собрать эталон

Раздать `author.csv` и `second.csv` раздельно. В бланках скрыты позиции, фолды,
старые оценки фильтра и ответы моделей. Первый разметчик заполняет весь набор,
второй — 120 заранее выбранных примеров разработки и весь закрытый тест.
В столбце `label` разрешены `relevant`, `irrelevant`, `insufficient_data`;
в `reason` записывается основание по карточке. Границы классов и примеры — в §2.1.

```bash
python scripts/hw3_data.py gold --split data/work/split --part dev \
  --out data/work/dev.jsonl
```

Скрипт выводит согласие, каппу Коэна и матрицу разногласий до согласования. Для
спорных пар создать локальный CSV со столбцами `id,label,reason` и повторить
команду с `--decisions data/work/decisions.csv`. Если согласие низкое, пересмотреть
инструкцию на разработке. Эталон test согласуют до просмотра прогнозов обеих моделей;
участники подбора конфигурации не используют тестовые строки.

## 3. Обучить бейзлайн и выбрать LLM на разработке

```bash
python scripts/hw3_experiment.py baseline --dev data/work/dev.jsonl --out data/work/baseline
python scripts/hw3_experiment.py llm-dev --dev data/work/dev.jsonl \
  --models "$MODEL_SMALL" "$MODEL_LARGE" --rub-hour "$RUB_PER_HOUR" --out data/work/llm
```

Для второй команды заранее установить и запустить локальную Ollama на
`127.0.0.1:11434` с двумя instruction-моделями. В `MODEL_SMALL` и `MODEL_LARGE`
указать точные, разные теги из `ollama list`. Перед использованием данных
отключить облачные функции сервера (`OLLAMA_NO_CLOUD=1`) и согласовать использование
снимка. Скрипт не скачивает модели. В `RUB_PER_HOUR` указать согласованную
стоимость часа машины. Локальную стоимость считаем по фактическому времени занятости.

У бейзлайна словари и веса IDF строятся заново только на обучающей части каждого
из пяти фолдов. Признаки — произведение и модуль разности векторов критериев
и компании, косинусное сходство, длина описания и совпадения слов критериев.
По объединённым отложенным прогнозам выбираются n-граммы, `min_df` и сила
регуляризации. Для сравнения сохраняется результат самого частого класса.

LLM получает один [промпт](../prompts/relevance-v1.txt), до трёх примеров из
обучающей части фолда и обезличенный текст карточки. Пустая карточка сразу
получает `insufficient_data`. Технический отказ учитывается отдельным исходом.
При возобновлении используются сохранённые законченные фолды, незаконченный
фолд запускается заново. Перед повтором сверить остаток бюджета (§1.2).
Среди вариантов, прошедших ограничения времени и стоимости на разработке,
выбирается лучший по Macro-F1, при равенстве — более дешёвый.

## 4. Проверить зафиксированную пару моделей

```bash
python scripts/hw3_data.py gold --split data/work/split --part test \
  --decisions data/work/decisions.csv --out data/work/test.jsonl
python scripts/hw3_experiment.py test --dev data/work/dev.jsonl --test data/work/test.jsonl \
  --baseline data/work/baseline --llm data/work/llm --out data/work/test-run
```

При отсутствии разногласий опустить `--decisions`. Код проверяет разделение
групп, версии кода, данных разработки, промпта и модели. На test один раз
сравниваются зафиксированные варианты. Сохранить контрольные суммы локальных файлов.
Из `report.json` перенести в этот отчёт агрегаты, включая численность по классам,
Macro-F1, precision/recall, потери подходящих компаний, покрытие, матрицу ошибок
и парный групповой 95% интервал разности Macro-F1. Указать названия и версии моделей,
стоимость и время пакетов. При разборе обоснований отдельно отметить число проверенных
ответов и долю объяснений, которые не подтверждаются карточками.
Полные прогнозы, тексты, бланки и обученный словарь остаются в `data/work/`.
Решение о допуске к пилоту учитывает отдельный нагрузочный прогон на 100 пакетах.
